# Архитектура iHealth Export

## SUMMARY

Один сервер объединяет приём данных, SQLite и MCP: разделение не даёт пользы для одного пользователя, но добавляет деплой и сетевое взаимодействие. iPhone остаётся единственным компонентом, имеющим доступ к HealthKit.

## Поток данных

```text
iPhone / HealthKit
  -> POST /upload/v1/batches
  -> Go server
  -> SQLite WAL volume
  -> POST /mcp
  -> MCP client
```

## Решения

- Один бинарник и контейнер: HTTP API и MCP используют один store.
- SQLite в WAL-режиме, один writer connection, batch применяется транзакционно.
- UUID HealthKit — первичный ключ. Повторная загрузка выполняет upsert.
- `HKQueryAnchor` хранится на iPhone отдельно для каждого типа и обновляется только после успешного ответа сервера.
- Удаления из HealthKit передаются как UUID и удаляются только для того же `device_id`.
- Временные метки передаются в UTC/RFC 3339. MCP также принимает календарную дату.
- MCP stateless: сервер не назначает session ID, поддерживает синхронные JSON-ответы Streamable HTTP.
- Один статический Bearer-токен защищает оба endpoint. Это достаточный компромисс только для личной локальной установки.

## Схема записи

Общие поля: UUID, HealthKit identifier, kind, начало/конец, источник, устройство, metadata и subtype payload. Числовые данные дополнительно имеют `value` и каноническую `unit`; тренировки — числовой и читаемый тип активности.

## Известные ограничения

- HealthKit не предоставляет API «перечислить все типы», поэтому каталог берётся из iOS 26 SDK и должен обновляться при появлении новых identifiers.
- Series-данные требуют отдельных запросов для точек и будут расширяться отдельно.
- Бесплатная Personal Team требует переподписи приложения раз в 7 дней.
- HTTP без TLS выбран пользователем для локального IP; при расширении зоны доступа HTTPS обязателен.
